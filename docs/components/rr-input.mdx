## Overview

Use `rr-input` for single-line text entry in a form — email, username, search, and the like. It is form-associated (participates natively in `<form>` submission via `ElementInternals`) and ships `label`, `helper-text`, and `error-text` as first-class props, wiring up `aria-describedby` / `aria-errormessage` for you. For multi-line text use a textarea; for choosing among fixed options use a select, radio, or checkbox.

## Accessibility

- **WAI-ARIA pattern:** [www.w3.org/WAI/ARIA/apg/patterns/textbox/](https://www.w3.org/WAI/ARIA/apg/patterns/textbox/)
- **Focusable:** yes
- **Keyboard:** Tab moves focus to the input; Standard text editing keys work natively
- **WCAG:** 1.3.1 Info and Relationships, 1.3.5 Identify Input Purpose, 1.4.3 Contrast (Minimum), 2.4.6 Headings and Labels, 3.3.1 Error Identification, 3.3.2 Labels or Instructions

**Rules**

- aria-errormessage points to error div; aria-describedby mirrors the link while invalid as AT fallback.
- When valid, aria-describedby points to helper text. When invalid, it switches to error text.
- delegatesFocus ensures host element forwards focus to inner <input>.
- ElementInternals.setFormValue() keeps the form value in sync with the input.

## Usage

- **Do** always provide a `label` — a placeholder is not a label (it vanishes on typing and isn't reliably announced).
- **Do** put validation messages in `error-text`; the component switches `aria-describedby` to it while invalid.
- **Do** set `type` and `autocomplete` accurately (e.g. `type="email"` + `autocomplete="email"`) so browsers and password managers assist correctly.
- **Don't** use `placeholder` to convey requirements — use `helper-text`, which stays visible.
- **Don't** rely on color alone for the error state — the `error-text` message must state what is wrong.
