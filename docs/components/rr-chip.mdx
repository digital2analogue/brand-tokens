## Overview

Use `rr-chip` for a discrete thing — a category, a keyword, a skill, a filter, a value someone chose. The split from `rr-badge` is **provenance, not interactivity**: a badge reports state the *system* decided and you cannot influence (status, count, validity), a chip names a thing. Ask who decided what it says, not whether it is clickable.

The visual treatment follows: `rr-badge` is a filled pill, `rr-chip` is square-cornered (`radius-sm`), transparent-filled and bordered. `variant="subtle"` steps down one more rung for dense contexts (table cells, long chip lists).

### One silhouette, four modes

A chip **never changes shape**. Interactive or not, latched or not, it is `radius-sm` — settled by the owner on 2026-09-03. What changes is the *affordance*, exactly as hard rule 5 describes: an operable chip earns the accent, a focus ring and Enter/Space.

That restraint is deliberate. A component that swapped outlines on a boolean would appear twice in a design file under two shapes, and nobody reading a mock could tell *"this chip is interactive"* from *"someone used the wrong radius"*.

| mode | what it is | what it renders |
|---|---|---|
| *(none)* | a label | a `span`, no role, not focusable |
| `interactive` | an operable chip | a real `<button>` — click, Enter, Space |
| `pressed` | a latched filter chip | `aria-pressed`, filled; implies `interactive` |
| `removable` | a value you can dismiss | a second button, sibling to the body |

`empty` layers on top of any of these: the awaiting-input treatment for a trigger with nothing chosen yet.

## Properties

| Prop | Type | Default | Description |
|------|------|---------|-------------|
| `variant` | `'default' \| 'subtle'` | `default` | Emphasis level. `default` is the standard visible outline (alt text, muted-foreground border) that reads correctly standalone — use it for skill chips and most labels. `subtle` is a quieter treatment (muted text, elevated-border) for dense or secondary contexts. |
| `interactive` | `boolean` | `false` | Makes the chip body a real button — focusable, with Enter and Space. The accent border and label come with it. Reflected. |
| `pressed` | `boolean` | `false` | Latched state for a filter chip; sets aria-pressed and fills the chip. Implies interactive. Controlled by the consumer — the chip does not toggle itself, so flip it on the click event. Reflected. |
| `removable` | `boolean` | `false` | Adds a trailing dismiss control that fires rr-chip-remove. Independent of interactive: a static value chip can be removable. Reflected. |
| `empty` | `boolean` | `false` | Renders the awaiting-input treatment — dashed edge, muted label — for a chip acting as a trigger with nothing chosen yet. Distinct from disabled: an empty chip is still operable. Reflected. |
| `disabled` | `boolean` | `false` | Disables the chip body and its dismiss control. Reflected. |
| `removeLabel` | `string` | `Remove` | Accessible name for the dismiss control. Name the thing being removed ("Remove Income filter") — a row of chips all saying "Remove" tells a screen-reader user nothing. Maps to attribute remove-label. |

## Slots & Events

### Slots

| Slot | Description |
|------|-------------|
| `default` | Chip label text. Rendered uppercase via CSS — pass normal-case text. |
| `leading` | Icon or marker before the label, inside the chip's own padding rhythm. |
| `trailing` | Icon or marker after the label. Not the remove control — that is the removable prop. |

### Events

| Event | Detail |
|-------|--------|
| `rr-chip-remove` | Bubbles (composed) when the dismiss control is activated. Not fired while disabled. The chip does not remove itself — the consumer decides what happens. |

## Accessibility

- **WAI-ARIA pattern:** [www.w3.org/WAI/ARIA/apg/patterns/button/](https://www.w3.org/WAI/ARIA/apg/patterns/button/)
- **Focusable:** yes
- **Keyboard:** Tab reaches the chip body when interactive or pressed, and the dismiss control when removable; Enter and Space activate the body and the dismiss control, via native buttons
- **WCAG:** 1.4.3 Contrast (Minimum), 1.4.11 Non-text Contrast, 2.1.1 Keyboard, 2.4.7 Focus Visible, 4.1.2 Name, Role, Value

**Rules**

- Chip text alone must convey meaning; do not rely on the border or emphasis level to communicate.
- A static chip exposes NO role and is not focusable — it renders a span. Only interactive, pressed and removable introduce controls, and each is a native button so Enter and Space come for free.
- aria-pressed is present only when pressed, and absent entirely otherwise — an unpressed toggle and a plain button are different things to a screen reader.
- The dismiss control carries its own accessible name via remove-label; name the value being removed, not the action alone.
- empty stays operable and keeps a legible edge. Never use disabled to mean "nothing chosen yet": disabled removes the control from the tab order and announces it as unavailable.
- Both variants meet WCAG AA for text contrast on the base canvas (default 8.0:1, subtle 6.3:1). Interactive uses foreground.action (11.1:1 on canvas, 9.0:1 on background.alt hover); pressed pairs foreground.accent-green on background.accent-green at 9.7:1.
- A chip used as a popup trigger must not declare aria-haspopup or aria-expanded — the popup owns those.

## Guardrails

**System rules** — how each is enforced in parentheses; `manual` means nothing checks it for you.

- `hard-1` _(lint)_ — No hardcoded colors — use var(--color-*) custom properties
- `hard-5` _(manual)_ — Accent green (foreground.action, foreground.accent, background.action, background.accent) is never resting text or decoration — it signals interactivity or intentional emphasis only
- `hard-6` _(gate)_ — All text must meet WCAG AA contrast (4.5:1) against its background — all pairings in the system already do; do not introduce new ones without checking
- `hard-9` _(lint)_ — Never use primitive tokens (color.green.*, space.*, font.size.*) in UI code — always go through the semantic layer
- `hard-10` _(lint)_ — Motion must respect `prefers-reduced-motion` (WCAG 2.3.3). The built brand CSS zeroes `--motion-duration-*` under `reduce`, so token-driven transitions stop automatically — never hardcode a transition/animation duration that bypasses the tokens. Any infinite animation (spin, shimmer, pulse) cannot be reached by the token override and MUST carry its own `@media (prefers-reduced-motion: reduce)` guard that stops or damps it

**Using rr-chip**

- Chip vs badge is a question of provenance, not interactivity. A badge reports state the system decided and you cannot influence — status, count, validity. A chip names a discrete thing — a category, a skill, a filter, a value someone chose. Pick by asking who decided what it says, not by whether it is clickable.
- A chip keeps ONE silhouette in every mode: radius.sm, interactive or not (owner's call, 2026-09-03). What changes is the affordance — an operable chip earns the accent, a focus ring and Enter/Space. Never change the radius to signal interactivity; a reader of a mock could not then tell an interactive chip from a wrong one.
- pressed implies interactive, and is CONTROLLED — the chip does not toggle itself, exactly like rr-tab[selected]. Listen for click and flip the prop. A chip that toggled itself would fight every consumer holding filter state of its own.
- removable is independent of interactive: a static value chip can carry a dismiss control. The control is a SIBLING of the body, never a child — a button inside a button is neither valid HTML nor operable — and its click is stopped so it cannot also read as a click on the chip.
- Name what the dismiss control removes via remove-label ("Remove Income filter"). A row of chips all announcing "Remove" tells a screen-reader user nothing about which one they are on.
- empty is awaiting-input, NOT disabled. It keeps a legible dashed border and stays fully operable; disabled recedes to near-canvas and stops accepting input. Reaching for disabled to mean "nothing chosen yet" tells the user the control is unavailable when it is in fact the next thing they should press.
- When a chip is used as the trigger for a popup, it must not declare aria-haspopup or aria-expanded itself. The popup stamps those onto whatever sits in its trigger slot, exactly as rr-menu already does — so the same chip stays correct when it is used as a plain filter.
- Do not point a chip border at --color-border-default for the resting state: it equals background.alt and disappears on the page canvas. The default variant uses foreground.muted and the subtle variant uses border.elevated so both stay visible standalone. (empty is the deliberate exception — a dashed border.default edge reads as an unfilled field.)
- Content is transformed to uppercase with --letter-spacing-all-caps in CSS; authors pass normal-case text and must not pre-uppercase it.

## Usage

- **Do** use chips in groups — a lone annotation is usually better as plain muted text.
- **Do** use `variant="subtle"` in dense surfaces (tables, list rows) where even the default border is loud.
- **Do** treat `pressed` as **controlled**. The chip does not toggle itself, exactly like `rr-tab[selected]` — listen for `click` and flip the prop. A self-toggling chip fights every consumer that holds filter state of its own.
- **Do** name what the dismiss control removes: `remove-label="Remove Income filter"`. A row of chips all announcing *"Remove"* tells a screen-reader user nothing about which one they are on.
- **Don't** put status meaning in a chip — success/warning/danger belongs to `rr-badge`, because the system decided it.
- **Don't** reach for `disabled` to mean *"nothing chosen yet"* — that is what `empty` is for. `disabled` drops the control out of the tab order and announces it as unavailable; `empty` keeps it operable behind a dashed edge, which is the difference between *you cannot use this* and *this is the next thing to press*.
- **Don't** give a chip `aria-haspopup`/`aria-expanded` when it triggers a popup — the popup stamps those onto its trigger slot, as `rr-menu` already does. That way the same chip stays correct as a plain filter.
- **Don't** nest the dismiss control inside the body. It is rendered as a *sibling*, because a button inside a button is neither valid HTML nor operable; its click is also stopped so removing a chip never doubles as clicking it.

### Composing a filter row

```html
<rr-chip interactive pressed>Design Systems</rr-chip>
<rr-chip interactive>Compliance UX</rr-chip>
<rr-chip interactive>Research</rr-chip>
```

### A trigger that has not been answered

```html
<rr-chip interactive empty>Select attribute</rr-chip>
```
